Section: "Security — DASC-Aligned, Requirements Through Threat Modeling"
1. Process statement (one paragraph):

Following IBM Consulting's guidance, we ran Digital AppSec Champion across all three stages — Control Generation (requirements), Gap Analysis (design), and Threat Modelling (STRIDE) — against a formal 23-requirement security specification and a full Data Flow Diagram of the application. 6 of 7 identified gaps were closed in code before submission; the 7th (a managed secrets store) is documented as a deployment-stage dependency, not a code gap.

2. Before/after table (this is the single most compelling artifact — use it directly):

Requirement	Before	After
SR-DP-4 — Encryption at rest	Plaintext JSON state file	AES-256-GCM authenticated encryption
SR-AU-2 — Corruption detection	Silent reset, no alert	GCM auth-tag verification + alertOps() (log + Slack alert)
SR-AV-3 — Predictable degradation	8 external API calls with no timeout, including the core Granite inference call	Every external call now has an explicit timeout
SR-TP-4 — Trusting third-party self-reports	(Reviewed — already correctly isolated to server-side logs)	Confirmed via code audit
SR-AC-5 — Role-based access	Single shared passcode, uniform access	Second passcode gates Final Approval specifically (the one irreversible action)
3. Honest scope note (this is what makes it credible, not just a checkbox exercise):

SR-DP-3 (secrets manager) and SR-AC-6 (full multi-user accounts) remain open — both require infrastructure or architecture decisions beyond what a code change can resolve at this stage, and are documented as the next security investment rather than silently deferred.

4. One line about tool quality, which shows judgment, not just tool usage:

The Threat Modelling module generated 537 raw findings; roughly a third referenced technology not present in this stack (e.g., Azure AD, HSMs — this app has neither). Findings were manually cross-referenced against the actual codebase before any were acted on, rather than accepted at face value.
