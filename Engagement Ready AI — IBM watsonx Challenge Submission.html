ICA integration = Agent API (A2A). The app POSTs a natural-language trigger message to the ICA Agentic App's A2A endpoint (servicesessentials.ibm.com/agenticapps/a2a/{appId}/agents/{agentId}) authenticated with ICA_A2A_KEY. This is the only ICA connection strategy this app uses in production. It has been live-tested end to end: a real POST to this exact endpoint returns a real conversation_id and a real agent response, confirmed today.

Two earlier architectures were explored and are intentionally not used — kept only as dated history, not as competing designs:

  • Direct ICA REST API (first attempt) — assumed ICA exposed conventional REST endpoints. It doesn't; superseded.
  • MCP-via-Orchestrate (second attempt) — assumed watsonx Orchestrate should broker the ICA MCP call. Correct in spirit, but the direct Agent API route proved simpler and is what's live today.

Deliverable 1

Solution Statement

What problem it solves, who it serves, and the expected productivity outcome.

The Problem

Before IBM Consulting begins any client engagement, a lead consultant must manually assess whether the engagement is ready to proceed — checking stakeholders, workshops conducted, requirements defined, risks identified, and open questions resolved. This process is entirely manual, inconsistent across teams, and typically takes 2 to 4 days per engagement of senior consultant time.

The current state:

  • Consultants trawl through unstructured workshop notes, meeting minutes, and email threads manually
  • No standardised scoring methodology — readiness is judged by experience and gut feel
  • Risks and gaps are discovered late, causing costly rework or delayed kick-offs
  • Task assignment after a review is ad hoc — Jira, Slack, and email done manually one-by-one
  • No full audit trail of who decided what, when, and why

The Solution

Engagement Ready AI is a full-stack Next.js 15 agentic application that replaces this manual process with a 10-step AI-governed workflow. The consultant pastes raw discovery notes; the system does the rest.

ICA Agent API — The Core Integration

The app calls ICA's Agent-to-Agent (A2A) endpoint using the Agentic App Studio Lab pattern:

# From Agentic App Studio Lab — implemented in services/ica-agent-api-service.ts
curl -X POST \
  "https://servicesessentials.ibm.com/agenticapps/a2a/{appId}/agents/{agentId}" \
  -H "Authorization: Bearer {ICA_A2A_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "message": "ASSIGN_TASKS: Post-assessment action plan accepted...",
    "context": {
      "trigger_action": "assign-tasks-and-notify",
      "context_id": "ctx_69dbd815ec49",
      "engagement_id": "eng-001",
      "action_plan": [...],
      "readiness_score": 72
    }
  }'

IBM watsonx.ai — 3-Agent Sequential Pipeline

watsonx.ai (Granite 3 8B Instruct) runs a strictly sequential 3-agent pipeline — no parallelism, each agent feeds the next:

#AgentInputOutput
1 Discovery Consolidator Raw workshop notes / transcripts pasted by consultant Structured JSON context package: stakeholders, workshops, requirements, risks, gaps
2 Delivery Readiness Analyst Structured context + Context Studio ontology Readiness score (0–100), decision, confidence, critical issues, recommendations, reasoning trace
3 Consulting Asset Generator Readiness analysis + action plan Action plan with per-role task assignments (Architect / Consultant / QA / Operations)
Strict separation of concerns: watsonx is ONLY the analyst — it scores, identifies risks, and plans. It never sends emails, creates Jira tickets, or posts to Slack. ICA is the executor of all actions.

IBM Context Studio (MCP Integration)

Context Studio provides the engagement knowledge base. The app uses the MCP gateway to query semantic context before every watsonx assessment:

  • Context ID: ctx_69dbd815ec49 — ingested via ContextForge (MCP server 3e49f953420a4cbcaf78a083586b4098)
  • MCP Gateway URL: servicesessentials.ibm.com/mcp-gateway/service/gateway/servers/8ccdd203…/mcp
  • Context Studio is queried using context-broker-hybrid-query (semantic + graph) before the assessment pipeline runs
  • The context snapshot is passed as shared state to all 3 watsonx agents
The real differentiator: this loop closes. Reading Context Studio before an assessment is table stakes — most AI tools that "check a knowledge base" stop there. This app also writes back. Every HITL decision (accept or override, with the consultant's justification) is posted to Context Studio as a new institutional-memory event via context-broker-post-events, scoped to the same context ID the next assessment reads from. Concretely: a live graph query against this context returned real nodes referencing prior ReadinessResult records — meaning Agent 2 (Delivery Readiness Analyst) is grounded in what this practice has actually decided before, not just static day-one documentation. The more engagements run through it, the better its judgment gets — without retraining a model or maintaining a prompt library by hand. That's a compounding accelerator, not a one-shot form-filler.

Security Design (DASC-aligned)

No credentials in source code All secrets via .env.local — Zod-validated at startup. Never in Git.
Zero PII in client bundle All IBM credentials, API keys, and stakeholder emails are server-side only.
Principle of least privilege ICA A2A key scoped to one app. Context Studio API key scoped to one context ID.
Human approval gates AI can never autonomously send emails, create Jira tickets, or approve engagements without explicit consultant confirmation.
Audit trail enforcement Every HITL decision, task completion, and status change is timestamped and persisted in immutable workflow state.
Graceful degradation Every IBM service call is guarded by hasXxxConfig(). Services return mock/log-only when credentials absent — never throw.

Pitch: Engagement Ready AI

3-page PDF / 3-minute video script content — ready to present to judging panel.

Slide 1 — The Problem (30 seconds)

"Every IBM Consulting engagement starts with a risk no one talks about: we don't actually know if we're ready to deliver."

Senior consultants spend 3–5 days per engagement manually reviewing workshop notes, checking stakeholders, scoring readiness, and writing the same emails and Jira tickets from scratch. It's inconsistent, time-consuming, and gets skipped under pressure. When gaps are found late, the cost is enormous.

Slide 2 — The Solution (60 seconds)

Engagement Ready AI is a live, working agentic application built on IBM watsonx.ai, IBM Consulting Advantage (ICA), and Context Studio. The consultant pastes their discovery notes — the system delivers a scored readiness assessment, assigns remediation tasks to the right people, tracks completion, and generates the full delivery package. All in under 15 minutes.

What makes it different:

  • The institutional-memory loop closes. It doesn't just read Context Studio before an assessment — every HITL decision writes back into it, so the next assessment is grounded in what this practice actually decided, not just static day-one docs. It gets better at judging readiness the more it's used — no retraining, no prompt-library upkeep.
  • Not just a chatbot — a full 10-step governed workflow with two human approval gates
  • ICA Agent API is called directly using the Agentic App Studio Lab curl pattern — live, not simulated
  • Human-in-the-Loop is architecturally enforced — AI recommends, humans decide, ICA executes
  • Every assessment produces a full explainable reasoning trace — consultants can see exactly why each decision was made

Slide 3 — Impact + Reusability (60 seconds)

12–18 hours saved per engagement. That's not a projection — it maps directly to the manual activities this system replaces: structured evidence review (3–4h), readiness scoring (4–6h), risk documentation (2–3h), task assignment (1–2h), executive summary (2–3h), client and internal emails (1–2h), and Jira creation (1–2h).

This is a team-wide accelerator, not a personal prompt. Any IBM Consulting practice can onboard their engagement context into Context Studio and get the same governed pipeline — the same standardised scoring, the same explainable reasoning, the same ICA-driven task assignment. The agent YAML and prompt artefacts are reusable, auditable, and refinable.

This is what Human-in-the-Loop actually looks like in practice: the consultant doesn't trust the AI blindly — they see the reasoning trace, can accept or override the recommendation, must personally approve the final engagement status, and ICA creates every Jira ticket only after both gates pass. The AI is the analyst. The human is still in charge.
