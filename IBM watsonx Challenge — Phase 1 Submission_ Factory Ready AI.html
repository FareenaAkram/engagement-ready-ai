01 Problem Statement

Every manufacturing shift begins with the same question: Is this production line actually ready to start? The answer requires synthesising data from at least four different enterprise systems — operator shift notes, maintenance work orders, QA hold status, and SCADA downtime events — none of which talk to each other.

Today, the Plant Manager does this manually. They read through 40–60 data points, form a mental model of risk, and make a judgement call. This typically takes 30–45 minutes per review, introduces human inconsistency, and happens without structured accountability when a block is missed and the line starts with unresolved issues.

The business consequence is real: a first-hour stoppage caused by a missed pre-shift blocker costs an average of 28 minutes of lost production, plus scrap, supervisor escalation time, and crew disruption.

The core problem: Pre-shift startup intelligence is manual, siloed, inconsistent, and slow — in an environment where a 30-minute error costs thousands of dollars in production value.
02 Solution Overview

Factory Ready AI is an AI Operations Control Center that replaces the manual pre-shift review with an automated, AI-driven workflow. The system:

  1. Auto-collects all relevant enterprise context — operator notes, maintenance logs, QA holds, downtime events, production schedule — without requiring the Plant Manager to enter data
  2. Runs a 3-agent IBM Granite pipeline that consolidates evidence, produces a startup decision with confidence score, and generates specific corrective tasks
  3. Routes those tasks to the right human role (maintenance, QA, supervisor) via watsonx Orchestrate
  4. Tracks the workflow from task assignment through completion through final startup authorisation — with a full timestamped audit trail
  5. Re-analyzes once blockers are resolved to confirm startup readiness before the supervisor gives final approval
Result: What takes 30–45 minutes manually now takes under 30 seconds of Plant Manager time. The AI handles the synthesis; the human handles the decision.

04 3-Agent Architecture

The system implements three cooperating agents as sequential IBM Granite inference calls. Each agent has an explicit role, input contract, output schema, and passes its structured JSON output to the next agent.

1
Evidence Consolidator

Operator Analyst Agent

Parses raw shift signals — operator notes, maintenance logs, QA holds, downtime events — and extracts structured evidence: active blockers, resolved items, open risks, and conflicting signals.

2
Startup Risk Analyst

watsonx.ai Reasoning Agent

Reads Agent 1's structured evidence and produces: startup decision (blocked / watchlist / startup-ready), confidence score (0–100), executive summary, critical issues, recommendations, affected machines, estimated delay.

3
Orchestration Packager

Orchestrate Coordinator Agent

Reads Agent 2's risk analysis and generates specific, owner-assigned tasks for maintenance, QA, and supervisor — referencing actual asset names, fault codes, and batch IDs from the analysis.

Key design principle: No agent re-reads the raw input. Each agent reads only the structured output of the previous agent. This creates a verifiable chain of reasoning and prevents the AI from losing context between steps.

Data flow between agents (actual implementation):

// services/watsonx-service.ts — real Granite pipeline // Agent 1: Evidence Consolidator runEvidenceConsolidator(token, input) → EvidencePackage { lineContext, activeBlockers, resolvedItems, openRisks, conflictingSignals } // Agent 2: Startup Risk Analyst (receives Agent 1 output) runRiskAnalyst(token, evidencePackage, input) → RiskAnalysis { startupDecision, confidenceScore, executiveSummary, criticalIssues[], recommendations[], affectedMachines[], estimatedDelayMinutes, businessImpact } // Agent 3: Orchestration Packager (receives Agent 2 output) runOrchestrationPackager(token, riskAnalysis) → OrchestrationOutput { workflowId, summary, nextApprover, tasks[{ id, title, ownerRole, instructions, dueLabel, priority }] }

06 watsonx.ai Integration — Technical Detail

The app uses IBM's production watsonx.ai inference API with real IAM token authentication. The integration is fully implemented in services/watsonx-service.ts.

Authentication: IAM token exchange with caching (30-second expiry buffer to prevent redundant calls).

// IAM token exchange — services/watsonx-service.ts POST https://iam.cloud.ibm.com/identity/token grant_type: 'urn:ibm:params:oauth:grant-type:apikey' apikey: WATSONX_API_KEY → Returns: { access_token, expires_in } → Cached with expiry (no repeated auth calls)

Inference endpoint:

// Each agent calls Granite directly POST https://us-south.ml.cloud.ibm.com/ml/v1/text/generation?version=2024-05-31 Authorization: Bearer <iam_token> { "model_id": "ibm/granite-3-8b-instruct", "project_id": "32b7e054-53cb-402c-b763-c5627d38a462", "input": "[system_prompt]\n\n[user_content]\n\nRespond only as compact JSON.", "parameters": { "decoding_method": "greedy", "max_new_tokens": 500, // varies per agent "stop_sequences": [] } }

Per-agent token tracking: Every agent call records generated_token_count and wall-clock duration. These are stored in AgentStepResult and displayed on the AI Analysis page's "Live pipeline trace" panel.

07 watsonx Orchestrate Integration — Technical Detail

The Orchestrate integration is fully implemented in services/orchestrate-service.ts. It uses the correct IBM Orchestrate Chat Completions API with IAM bearer token authentication — the same pattern as watsonx.ai.

Current status: The integration code is production-ready and tested. Activation requires adding ORCHESTRATE_URL and ORCHESTRATE_AGENT_ID to .env.local (see Section 10). The same IBM Cloud API key used for watsonx.ai also authenticates Orchestrate.

API endpoint used:

// IBM Orchestrate Chat Completions API POST {ORCHESTRATE_URL}/v1/workspace/agents/{ORCHESTRATE_AGENT_ID}/chat/completions Authorization: Bearer <iam_token> Content-Type: application/json { "messages": [ { "role": "user", "content": "FACTORY READY AI — STARTUP READINESS WORKFLOW\nWorkflow ID: ...\nSummary: ...\nTASKS TO DISPATCH:\n..." } ], "metadata": { "workflow_id": "orch-1234567890", "tasks": [ { "id": "task-01", "title": "Verify cartoner sensor alignment", "owner_role": "maintenance", "priority": "critical", "due_label": "Before shift start", "instructions": "Inspect sensor alignment on Cartoner C-220..." } ], "next_approver": "Ariana Brooks", "source": "factory-ready-ai" } }

What the Orchestrate agent receives: A structured natural language message summarising the workflow, plus a full machine-readable metadata object containing all task assignments. The Orchestrate agent can then route each task to the correct skill owner inbox based on owner_role.

Fallback behaviour (when credentials not set): The service logs the full plan to the server console — including every task title, owner role, priority, and instructions — so the architecture is fully verifiable without a live Orchestrate tenant.

10 How to Add Real watsonx Orchestrate

The integration code is already written. You only need to provision a tenant and add 3 lines to .env.local.

Step 1

Provision watsonx Orchestrate

Go to cloud.ibm.com → Catalog → watsonx Orchestrate. Provision a trial or paid instance. You will receive a tenant URL in the format:
https://dl.us-east.watson-orchestrate.ibm.com/instances/<instance-id>

Step 2

Create an Orchestrate Agent

Inside the Orchestrate console, create a new agent. Name it factory-ready-ai. Configure it to receive structured workflow dispatch messages. Copy the Agent ID.

Step 3

Add 3 lines to .env.local

The same IBM Cloud API key you already have for watsonx.ai authenticates Orchestrate too:

# Already working — watsonx.ai WATSONX_API_KEY=keI8Yyh1fVvWdivfIi7NB44GAN62bwNBJiHxojc7lozs WATSONX_PROJECT_ID=32b7e054-53cb-402c-b763-c5627d38a462 # Add these 3 lines to enable live Orchestrate dispatch ORCHESTRATE_API_KEY=<same IBM Cloud API key as above> ORCHESTRATE_URL=https://dl.us-east.watson-orchestrate.ibm.com/instances/<your-instance-id> ORCHESTRATE_AGENT_ID=factory-ready-ai
That's all. No code changes needed. When these 3 variables are present, the next readiness review will dispatch tasks to your live Orchestrate agent via the Chat Completions API. The integration status badge on the Readiness Review page will change from "mock" → "live".

12 Phase 2 Roadmap

Phase 1 establishes the AI core and end-to-end workflow. Phase 2 would extend to make the system production-deployable:

  • →
    Replace mock adapters with real enterprise connectors: SAP PM for maintenance work orders, IBM Maximo for asset history, MES for operator notes, OSIsoft PI / SCADA for downtime events
  • →
    watsonx.governance integration: Register all Granite calls in the model registry, add PII scanning, add confidence thresholds and human-in-loop gates for high-risk decisions
  • →
    Real Orchestrate skill definitions: Define OpenAPI-compliant Orchestrate skills for each task type (maintenance verification, QA disposition, supervisor approval) so tasks appear in real user inboxes
  • →
    RAG for maintenance history: Index past work orders and fault codes in Elasticsearch + watsonx.ai embeddings to give Agent 2 historical context ("this asset had 3 jams in the last 30 days")
  • →
    Multi-line support: Scale from one production line to a plant-wide dashboard with per-line review workflows
  • →
    Fine-tuning on domain data: Fine-tune Granite on historical shift reports and resolution outcomes to improve domain accuracy for manufacturing-specific fault patterns
  • →
    Real-time streaming: Replace polling with SSE/WebSocket so pipeline stages update live across all open browser tabs simultaneously
  • →
    IBM Cloud deployment: Deploy on IBM Cloud Code Engine or IBM Cloud Kubernetes Service with IBM Secrets Manager for credential management
Commercial opportunity: The architecture is domain-agnostic. The same 3-agent pattern (Evidence Consolidator → Risk Analyst → Orchestration Packager) applies to pharmaceutical batch release, aircraft pre-flight checklists, hospital shift handoffs, and any regulated industry with multi-source evidence and human approval chains.
