1 · What ICA Actually Is

IBM Consulting Advantage (ICA) is IBM's internal proprietary platform for IBM Consulting engagements. It is not a public SaaS product you can sign up for — it is an IBM-internal system used by IBM consultants to manage:

  • Engagement projects and client workspaces
  • Delivery assets and document repositories
  • Stakeholder notifications and approvals
  • Task boards and action tracking
  • AI-assisted consulting accelerators (templates, playbooks, etc.)
Important: ICA does NOT have a publicly documented REST API available to all developers. Access to ICA's API is available to IBM employees and IBM Business Partners through IBM's internal developer portal. If you are an IBM employee, you can get ICA API credentials from the ICA Admin console or your IBM account team. If you are not an IBM employee, ICA will run in demo/mock mode — the app logs every payload it would have sent, which is architecturally transparent and acceptable for the challenge demo.

What the app does with ICA (when configured)

The app makes three REST API calls to ICA after the consultant clicks "Deliver Assets":

CallICA EndpointWhat it does
1 Push deliverablePOST /engagements/{id}/deliverablesStores all AI-generated assets (executive summary, risk register, open questions, etc.) in ICA's document repository, linked to the engagement.
2 Trigger notificationsPOST /engagements/{id}/notificationsICA sends email + Slack + Teams to all stakeholders registered on that engagement inside ICA. One call drives all channels.
3 Create tasksPOST /engagements/{id}/tasksCreates one follow-up task per critical issue in ICA's project board, assigned to the correct consultant or architect role.

3 · How to Configure ICA in the App

Step 1 — Get ICA API credentials (IBM employees only)

1

Log into IBM w3 / IBM internal developer portal

Go to w3.ibm.com → search "Consulting Advantage API" → navigate to ICA Admin > Integrations > API Keys. Or ask your IBM account team for the ICA API access program.

2

Create an API key scoped to your ICA instance

In ICA Admin, create a service account API key with permissions: deliverables:write, notifications:write, tasks:write. Copy the key.

3

Get your ICA instance URL

It will be something like https://api.ibm.com/consulting-advantage/v1 or https://<region>.consulting-advantage.ibm.com/api/v1. Check ICA Admin > Integrations > API.

4

Add to .env.local

ICA_API_KEY=<your-api-key>
ICA_URL=https://api.ibm.com/consulting-advantage/v1
5

Restart the dev server

npm run dev

The app reads .env.local at startup. The ICA channel in "Deliver Assets" will now say "configured" instead of "demo mode".

4 · Do You Need to Create an Assistant in ICA?

No, you do not need to create an assistant inside ICA.

The app does not use ICA as an AI assistant. It uses ICA purely as a delivery platform — pushing documents, triggering notifications, and creating tasks via ICA's REST API.

Here is the distinction:

ApproachWhat it meansDo we use it?
ICA as AI assistant Chat with an ICA-hosted AI agent that uses ICA's knowledge base and tools No — our AI is watsonx.ai (Granite)
ICA as delivery platform POST assets, notifications, and tasks into ICA via its REST API Yes — this is exactly what we do
ICA Orchestrate skills Create ICA-native workflow skills that can be triggered by watsonx Orchestrate Phase 2 — connect Orchestrate to ICA skills

Our AI pipeline lives entirely in watsonx.ai (IBM Granite). ICA only receives the finished output. This is the correct architecture — your AI stays in watsonx, your delivery stays in ICA.

5 · Configure Slack

Slack is a direct webhook — no IBM account needed. Takes 2 minutes.

1

Go to api.slack.com/apps

Click "Create New App" → "From scratch" → name it "Engagement Ready AI" → select your workspace.

2

Enable Incoming Webhooks

In your app settings → "Incoming Webhooks" → toggle on → "Add New Webhook to Workspace" → choose the channel (e.g. #engagements) → copy the webhook URL.

3

Add to .env.local

SLACK_WEBHOOK_URL=https://hooks.slack.com/services/T.../B.../...
4

Restart and test

Run an assessment, go to Consulting Assets, click "Deliver assets". The Slack channel will receive a rich card with readiness score, executive summary, critical issues count, and HITL decision.

6 · Configure Email (SMTP)

Works with Gmail, Outlook, SendGrid, or any SMTP server. Gmail example:

1

Enable 2-Step Verification on your Gmail account

Required before you can create an App Password. Go to myaccount.google.com → Security → 2-Step Verification.

2

Create a Gmail App Password

myaccount.google.com → Security → App Passwords → choose "Mail" → "Other" → name it "Engagement Ready AI" → copy the 16-character password.

3

Add to .env.local

EMAIL_SMTP_HOST=smtp.gmail.com
EMAIL_SMTP_PORT=587
EMAIL_USER=you@gmail.com
EMAIL_PASS=xxxx xxxx xxxx xxxx
EMAIL_FROM=Engagement Ready AI <you@gmail.com>
EMAIL_DEFAULT_RECIPIENT=recipient@example.com
4

Restart and test

You can also override the recipient per delivery by entering an email in the "Recipient email" field on the Consulting Assets page.

7 · Configure watsonx Orchestrate

Orchestrate dispatches the action plan after every assessment. Optional — app works without it.

1

Provision a watsonx Orchestrate instance on IBM Cloud

cloud.ibm.com → Catalog → search "watsonx Orchestrate" → create instance → copy the instance URL from the dashboard.

2

Create an agent in Orchestrate

In Orchestrate UI → Agents → New Agent → name it "Engagement Ready AI" → copy the agent ID from the URL or API. No skills needed for the MVP — the app sends it chat messages containing the full action plan.

3

Add to .env.local

ORCHESTRATE_API_KEY=<your IBM Cloud API key>
ORCHESTRATE_URL=https://dl.us-east.watson-orchestrate.ibm.com/instances/<instance-id>
ORCHESTRATE_AGENT_ID=<your-agent-id>

9 · Full Technical Flow — Step by Step

From opening the app to marking engagement ready

1

Browser opens → /dashboard

app/dashboard/page.tsx renders DashboardView. AppShell fires two React Query fetches: GET /api/dashboard and GET /api/ai-analysis. Results hydrate Zustand store via hydrateFromServer(). If no assessment has run, shows empty state with "Start assessment" CTA. If prior state exists in .next/tmp/workflow-state.json, shows it.

2

Consultant navigates to New Assessment → /readiness-review

Pastes discovery notes into the textarea. Optionally adds a consultant comment. Word count shown live. "Load sample" fills in a Meridian Financial Group example. Clicks "Run AI assessment".

3

POST /api/readiness-review fires

Body: { projectContext, consultantComment }. Calls submitReadinessReview() in services/dashboard-service.ts. Simultaneously, the UI simulates step progression (step 1 at 0ms, step 2 at 1800ms, step 3 at 3600ms) so the user sees pipeline progress in real time.

4

Server: pipeline starts — startPipelineRun()

Clears previous pipeline trace. Records collecting-data stage. Calls buildWatsonxPrompt() to build the prompt artifact (for display). Then calls runWatsonxPipeline().

5

watsonx.ai: Agent 1 — Discovery Consolidator

Gets IBM IAM token (cached 55 mins). Calls POST https://us-south.ml.cloud.ibm.com/ml/v1/text/generation with Granite 3-8B. System prompt: parse discovery notes. Returns JSON with: businessObjectives[], functionalRequirements[], nonFunctionalRequirements[], identifiedRisks[], missingInformation[], conflictingSignals[], stakeholdersIdentified[]. Max 500 tokens.

6

watsonx.ai: Agent 2 — Delivery Readiness Analyst

Takes Agent 1 output. Calls Granite again. System prompt: evaluate delivery readiness. Returns JSON: readinessDecision (ready / ready-with-conditions / not-ready), readinessScore (0–100), confidenceScore, criticalIssues[], recommendations[], openQuestions[], estimatedTimeSavedHours. Max 700 tokens.

7

watsonx.ai: Agent 3 — Consulting Asset Generator

Takes Agent 2 output. Calls Granite. Returns an action plan JSON: workflowId, tasks[] (each with ownerRole, priority, instructions, dueLabel). Max 600 tokens.

8

Server: build consulting assets + action plan

buildConsultingAssets() creates 6 draft asset cards (Executive Summary, Risk Register, Recommendations, Open Questions, Missing Information, Next Workshop Agenda). buildActionPlanFromPipeline() maps agent tasks to ConsultingActionTask[].

9

Server: dispatch to watsonx Orchestrate

dispatchOrchestrationPlan() builds a message containing the full action plan and POSTs to the Orchestrate agent chat endpoint. If not configured, logs the payload. Updates integrationStatus.orchestrate in the result.

10

Server: persist result to .next/tmp/workflow-state.json

persistReviewResult() writes the full AIAnalysisResult, advances workflow stage to actions-created, increments assessment count, adds to history (max 10). Records pipeline stage as completed.

11

Client: receives response → updates store + shows result

setReviewResult(data, workflow) updates Zustand store. Toast shows readiness score + decision. Assessment result card appears below the form. "View AI findings" button navigates to /ai-analysis.

12

Consultant reviews AI findings → /ai-analysis

Fetches GET /api/ai-analysis. Shows: executive summary, readiness decision + score, confidence, critical issues, open questions, recommendations, consulting asset drafts, pipeline trace (if live), agent chain definitions, watsonx prompt artifact, integration status badges.

13

HITL Decision — the critical step

Consultant sees the AI recommendation panel. Two buttons: Accept recommendation or Override recommendation. If override: dropdown to select different status + required justification textarea. On submit: POST /api/hitl-decision with HITLRecord (aiRecommendation, aiScore, consultantDecision, consultantChoice, justification, decidedAt). Server writes HITL record to workflow state, advances stage to engagement-ready. Store updated. Toast fires.

14

Consultant reviews actions → /maintenance-tasks

Views AI-generated consulting actions with owner, priority, due date. "Acknowledge actions" button fires PATCH /api/advance-stage → { stage: 'consultant-review' }. Workflow advances. Toast fires.

15

Consultant delivers assets → /qa-review

Reviews and edits 6 asset cards inline. Selects delivery channels (ICA, Slack, Email). Optionally enters recipient email. Clicks "Deliver assets". POST /api/notify fires all channels in parallel. Each channel returns { sent, live, error? }. Result badges shown per channel.

16

Engagement marked ready — timeline + dashboard

Timeline at /workflow-timeline shows full audit trail: all pipeline stages with real timestamps, workflow stage progress, HITL record (AI recommendation vs consultant decision + justification), engagement-ready banner. Dashboard shows readiness score, HITL record, open actions, time saved.

10 · Gaps That Could Block Phase 2

GapSeverityDetail
Engagement name/client hardcoded Critical The delivery package always sends "Meridian Financial Group / Core Banking Modernization". Phase 2 needs an input field on the New Assessment page so the consultant enters the real engagement name and client.
Single engagement only Critical The app stores exactly one assessment in a JSON file. Phase 2 needs a real database (PostgreSQL / Cloudant) and support for multiple engagements per user.
No authentication Critical Anyone with the URL can see all data. Phase 2 needs IBM w3 SSO (SAML/OIDC) so only IBM employees can log in, and engagement data is scoped per consultant.
JSON file persistence Critical State stored in .next/tmp/workflow-state.json. Wiped on every redeploy. Phase 2 needs a proper database.
ICA API not publicly documented High ICA integration runs in mock mode unless you have IBM employee access. Challenge judges need to see the mock payloads in console logs and understand this is architecturally correct.
Granite token limits High Each agent call is capped at 500–700 tokens. For long discovery notes, Granite may truncate. Phase 2 needs chunking + RAG or a larger context window model.
Orchestrate action plan not used by Orchestrate High The app sends the action plan as a chat message to Orchestrate. Phase 2 needs real Orchestrate skills (OpenAPI tools) so Orchestrate can actually execute actions — not just receive them as text.
No retry or error recovery Medium If Agent 2 fails mid-pipeline, the whole assessment fails with a 500. Phase 2 needs per-agent retry with exponential backoff.
Assets not truly editable Medium Edits to asset content in the UI are local state only — not persisted to the server. Close the tab and edits are gone. Phase 2 needs a save endpoint.
No file upload Medium The app only accepts pasted text. Phase 2 needs PDF/Word/PowerPoint upload with extraction, so consultants can upload existing decks directly.
Assessment count persists but not user-scoped Medium The counter in Analytics is global, not per consultant. Once multi-user auth is added, each consultant needs their own history.
No real action status updates Low Action statuses (pending / in-progress / completed) cannot be updated in the UI. Phase 2 needs action status mutation endpoints.

New features for Phase 2

  • Multi-engagement dashboard — list of all engagements, filterable by readiness status, client, lead consultant, date range.
  • Reassessment flow — after actions are resolved, run a second assessment against the same engagement. Track score improvement over time.
  • RAG on IBM playbooks — index IBM Garage Method, IBM Consulting Advantage templates, and past engagement patterns into a vector DB. Agent 2 retrieves relevant playbook sections before making its readiness decision.
  • Orchestrate skills — real tools: scheduleWorkshop(), createJiraTicket(), sendCalendarInvite(), updateCRMOpportunity(). Orchestrate executes these when an action is created, not just receives a message.
  • Executive reporting — monthly engagement readiness report, exportable, auto-sent to partners.
  • IBM Carbon Design System — full Carbon component library, proper IBM theming, accessible.
  • Governance dashboard — all HITL decisions across all consultants, override rate, AI accuracy tracking over time.
  • Proposal generator — use Granite to draft a full Scope of Work / Statement of Work from the engagement assets, ready for client review.

What makes this a genuine IBM product (not just a demo)

  • IBM w3 SSO makes it IBM-employee-only — trusted, auditable identity.
  • ICA as the primary delivery surface — assets live where IBM consultants actually work.
  • Granite models on IBM Cloud — all data stays within IBM's security boundary.
  • HITL as governance — every AI decision is counter-signed by a human consultant, audit trail in ICA.
  • IBM Consulting Advantage asset templates — not generic documents, actual ICA-compatible structured deliverables.
  • Quantified ROI — every assessment records estimated time saved, aggregated per practice, reportable to leadership.
