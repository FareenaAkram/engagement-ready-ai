ICA Reality — What Those Two API Keys Are + Docuflow Integration

Engagement Ready AI · IBM watsonx Challenge · July 2025

1 · What Those Two API Keys in ICA Actually Are

When you go to ICA Settings → Create API, it creates two keys. Here is exactly what they are:

Key NameWhat it isWhat it does
Cline Plugin VS Code / Cline AI coding assistant API key Lets the Cline VS Code extension (an AI coding agent) connect to ICA's knowledge base and tools. When a developer uses Cline inside VS Code, it can read ICA project context, pull assets, and take actions — all from inside their editor.
Root Plugin / Coding Agent MCP (Model Context Protocol) server key Exposes ICA as an MCP server. Any MCP-compatible AI agent (Claude, watsonx Orchestrate, Cursor, etc.) can connect to ICA using this key and use ICA as a tool — reading engagements, writing assets, triggering notifications — through the standard MCP protocol.
In plain English: ICA does not have a traditional REST API for your app to call. Instead, it exposes itself as an MCP server. Your AI agent (watsonx Orchestrate or Granite) connects to ICA via MCP using the "Root Plugin" key, and ICA becomes a tool the agent can use — not an endpoint your app directly POSTs to.
This means our current ica-service.ts is wrong about how it connects. It is built as a direct REST API client (POST /engagements/{id}/deliverables) — but ICA does not expose those endpoints publicly. The real integration path is MCP, not direct REST. This needs to be fixed.

2 · What Docuflow Is

Docuflow-AI is a separate IBM Consulting product — an agentic AI document processing workflow platform. It is not part of our application. It is relevant to us because:

  • It is an ICA-connected agent that processes documents using AI (extract, validate, act)
  • It uses the same ICA MCP integration pattern we need to implement
  • Its architecture (upload → extract → validate → act via agents) maps closely to what our app does (paste notes → consolidate → analyse → deliver)
  • It demonstrates that the correct ICA integration pattern is agent-to-ICA via MCP, not REST API
Should we integrate Docuflow into our app? Not directly — Docuflow is a separate IBM product that requires its own deployment. But we should mirror its integration pattern: use the ICA MCP server key to connect watsonx Orchestrate to ICA, so Orchestrate can push assets and trigger notifications inside ICA as a tool — exactly how Docuflow's agents do it.

Option B — Direct MCP client call (for the challenge demo)

Replace the fake REST calls in ica-service.ts with a proper MCP client call using the Root Plugin key. There is an official MCP TypeScript SDK:

# Install the MCP client SDK
npm install @modelcontextprotocol/sdk
// ica-service.ts — updated for real MCP
import { Client } from '@modelcontextprotocol/sdk/client/index.js';
import { StreamableHTTPClientTransport } from '@modelcontextprotocol/sdk/client/streamableHttp.js';

async function deliverViaICAMCP(pkg: ICAEngagementPackage) {
  const transport = new StreamableHTTPClientTransport(
    new URL(process.env.ICA_MCP_URL ?? ''),
    { headers: { Authorization: `Bearer ${process.env.ICA_MCP_KEY}` } }
  );

  const client = new Client({ name: 'engagement-ready-ai', version: '1.0' });
  await client.connect(transport);

  // Call ICA's MCP tools directly
  await client.callTool({ name: 'ica.createDeliverable', arguments: { ...pkg } });
  await client.callTool({ name: 'ica.notifyStakeholders', arguments: { engagementId: pkg.engagementId } });
  await client.callTool({ name: 'ica.createTask', arguments: { tasks: pkg.criticalIssues } });

  await client.close();
}
Important: The exact MCP tool names (ica.createDeliverable etc.) depend on what ICA's MCP server exposes. You need to call client.listTools() first to see what tools are available in your ICA MCP server. Run this once to discover them:

const tools = await client.listTools(); console.log(tools);
