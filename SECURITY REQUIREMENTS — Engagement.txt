SECURITY REQUIREMENTS — Engagement Ready AI
Prepared for: DASC Control Generation (requirements-through-threat-modeling)
Status key: [MET] = implemented and verified in code today. [GAP] = not yet
implemented — please prioritize controls for these.

=== 1. SCOPE ===
Engagement Ready AI is a Next.js consulting-productivity web application. A
single consultant role operates it per session; it processes client
engagement content (discovery notes, risk narratives), stakeholder PII
(names/emails), and holds live credentials for IBM watsonx.ai, IBM
Consulting Advantage (Agent API + Langflow MCP), IBM Context Studio (MCP),
Jira Cloud, Slack, and SMTP email. It triggers real, irreversible
side effects (sent emails, Slack messages, Jira tickets) after human
approval gates. Current deployment: local dev server exposed via ngrok for
demo purposes — not yet a production/multi-tenant deployment.

=== 2. AUTHENTICATION AND ACCESS CONTROL ===
SR-AC-1 [MET] — The system SHALL require a valid session credential before
  granting access to any application route or API endpoint, except for
  endpoints authenticated by an independent mechanism appropriate to their
  caller (e.g., a cryptographically signed inbound webhook).
SR-AC-2 [MET] — A session credential SHALL NOT reveal the underlying shared
  secret if intercepted or exfiltrated (i.e., the credential stored/
  transmitted must not be the secret itself).
SR-AC-3 [MET] — Comparison of any authentication credential against its
  expected value SHALL be performed in constant time to prevent timing-based
  disclosure.
SR-AC-4 [MET] — Destructive or irreversible operations (e.g., resetting
  engagement state) SHALL require an explicit confirmation signal distinct
  from, and in addition to, a valid session.
SR-AC-5 [GAP] — The system SHALL enforce role-based authorization so the
  four modeled roles (architect, consultant, partner, client) have
  independently scoped permissions once inside the session gate, rather than
  uniform access for any valid session.
SR-AC-6 [GAP] — The system SHALL support more than one independently
  authenticated user identity (moving beyond a single shared passcode) if
  deployed for more than one concurrent operator.

=== 3. DATA PROTECTION ===
SR-DP-1 [MET] — All communication between the client browser and the
  application server, and between the application server and third-party
  IBM/SaaS services, SHALL occur over TLS.
SR-DP-2 [MET] — Credentials for third-party services SHALL NOT be committed
  to version control (enforced via .gitignore on all secret-bearing files).
SR-DP-3 [GAP] — Long-lived third-party credentials SHALL be stored in a
  managed secrets store rather than plaintext environment files, and SHALL
  be rotatable without a code change.
SR-DP-4 [GAP] — Persisted engagement state (client business content,
  stakeholder PII) SHALL be encrypted at rest and SHALL include integrity
  verification sufficient to detect tampering or corruption, rather than
  silently resetting to default values.
SR-DP-5 [MET] — Log output SHALL NOT include full client business content
  (complete document text, complete email bodies) or recipient PII beyond
  what is required for operational debugging; counts and status SHALL be
  logged in preference to content.

=== 4. INPUT VALIDATION AND AI-SPECIFIC CONTROLS ===
SR-IV-1 [MET] — Free-text input accepted from a consultant (discovery notes,
  comments) SHALL be size-bounded before being submitted to any downstream
  processing or third-party API.
SR-IV-2 [MET] — Any large-language-model prompt that incorporates untrusted
  or consultant-supplied free text SHALL explicitly instruct the model to
  treat that text as data to analyze, not as instructions to follow, and
  that text SHALL NOT be able to alter the model's role, output schema, or
  decision logic.
SR-IV-3 [MET] — Output returned by a large language model SHALL be schema-
  validated before being persisted or acted upon; malformed or incomplete
  output SHALL trigger a defined fallback rather than propagating undefined
  or wrongly-typed values to downstream code.

=== 5. AVAILABILITY AND RESOURCE PROTECTION ===
SR-AV-1 [MET] — Any endpoint that invokes a metered or cost-incurring
  third-party API SHALL itself enforce a rate limit per caller.
SR-AV-2 [MET] — A single caller SHALL NOT be able to trigger unbounded
  consumption of a paid third-party API through automated or repeated
  requests.
SR-AV-3 [GAP] — The system SHOULD degrade predictably (documented, tested
  failure mode) rather than crash when a third-party API it depends on is
  unreachable or rate-limits the application itself.

=== 6. THIRD-PARTY INTEGRATION SECURITY ===
SR-TP-1 [MET] — Inbound webhook callbacks from a third-party service (e.g.,
  Slack interactivity) SHALL be authenticated via a mechanism that verifies
  the request originated from that service (e.g., a signed-request
  signature with replay-window enforcement), independent of the
  application's own session mechanism.
SR-TP-2 [MET] — Server-to-server pull requests from a trusted external
  system (e.g., IBM Consulting Advantage retrieving a delivery package)
  SHALL be scoped to an unguessable identifier and SHALL NOT expose data
  beyond what that specific integration requires.
SR-TP-3 [MET] — Real-world, irreversible side effects triggered via a
  third-party integration (sending email, posting to Slack, creating a Jira
  ticket) SHALL only occur after an explicit human approval step recorded in
  the system — never as a fully automated response to AI output alone.
SR-TP-4 [GAP] — Claims of a completed third-party action reported by an
  external agent (e.g., an AI agent self-reporting "email sent") SHALL NOT
  be trusted as proof of delivery; the application SHALL independently
  verify or itself execute any action it needs to guarantee occurred.
  (Currently satisfied for email; not yet formalized as a general policy
  covering all integration paths.)

=== 7. AUDITABILITY ===
SR-AU-1 [MET] — Every human decision that gates an irreversible action
  (accept/override of an AI recommendation, final delivery approval) SHALL
  be recorded with a timestamp and an attributed actor.
SR-AU-2 [GAP] — The system SHOULD detect and alert on corruption or
  unexpected reset of its persisted state, rather than silently falling back
  to default values with no diagnostic trace.

=== 8. OUT OF SCOPE FOR THIS SUBMISSION STAGE ===
- Multi-tenant isolation (single shared engagement context by design at this
  stage of the project)
- Formal penetration testing / red-team exercise
- Compliance certification (SOC 2, ISO 27001) — future direction, not a
  current requirement for a challenge-stage prototype

=== INSTRUCTION TO DASC ===
Please generate tailored controls against the requirements above,
prioritizing the [GAP] items (SR-AC-5, SR-AC-6, SR-DP-3, SR-DP-4, SR-AV-3,
SR-TP-4, SR-AU-2). For [MET] items, controls confirming/hardening the
existing implementation are welcome but should not assume a from-scratch
