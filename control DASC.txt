Project: Engagement Ready AI
Type: Web application (internal consulting productivity tool)
Stage: Working prototype / challenge submission — not yet production-deployed

Hosting platform: Currently local Node.js dev server exposed via an ngrok tunnel
  for live demos. No cloud deployment yet — target would be IBM Cloud or Vercel-
  style Node.js hosting.
Coding language / framework: TypeScript (strict mode), Next.js 15 (App Router),
  React 19.
Runtime dependencies: Zustand (client state), TanStack Query (data fetching),
  Zod (schema validation), Nodemailer (SMTP), @modelcontextprotocol/sdk (MCP
  client), Tailwind CSS v4.
Persistence: No database. All server state is a single JSON file on local disk
  (.next/tmp/workflow-state.json) — deliberate architecture choice for
  auditability and zero infra overhead.

External integrations (all via real HTTP/MCP calls, live credentials):
  - IBM watsonx.ai (Granite models) — text generation API, IAM bearer token auth
  - IBM Consulting Advantage Agent API (A2A) — REST, static API-key auth
  - IBM Consulting Advantage via Langflow — MCP (Streamable HTTP), x-api-key auth
  - IBM Context Studio — MCP (Streamable HTTP) gateway, dual header auth
    (Authorization Bearer + x-api-key)
  - Jira Cloud REST API v3 — Basic Auth (email + API token)
  - Slack Incoming Webhooks — URL-embedded secret
  - Slack Web API (bot) — OAuth bot token, for posting interactive messages
  - Slack Events/Interactivity callback — inbound webhook, HMAC-SHA256 signed
    request verification (implemented)
  - SMTP (Gmail/generic) — username + app password auth, via Nodemailer

Data processed:
  - Client engagement content: discovery notes, workshop transcripts, risk
    narratives, executive summaries (pasted as free text or uploaded as files —
    PDF/DOCX/TXT extracted server-side)
  - Stakeholder PII: names and email addresses (4 roles: architect, consultant,
    partner, client)
  - IBM service credentials and one Jira/SMTP credential set, all stored as
    plaintext environment variables in a local .env.local file — no secret
    manager or vault currently in use

Authentication / access control: a shared-secret passcode gate (Next.js
  middleware) now sits in front of every route. A visitor without a valid
  session cookie is redirected to a passcode screen (page routes) or gets a
  401 (API routes). The cookie stores an HMAC derived from the passcode, not
  the passcode itself, verified via constant-time comparison — no server-side
  session storage needed. Two routes are deliberately exempt because they
  can't hold our cookie: Slack's interactivity callback (verified instead via
  its own HMAC-signed request) and ICA's server-to-server package-pull
  endpoint. This is a lightweight single-shared-secret gate, NOT full
  user accounts or per-role authorization — the 4 modeled roles
  (architect/consultant/partner/client) still aren't independently
  authenticated once inside the gate.

Other controls already implemented:
  - Destructive state reset requires an explicit { confirm: true } body.
  - Agent system prompts instruct the model to treat pasted discovery notes
    as data, never as instructions (prompt-injection mitigation).
  - Pasted discovery notes capped at 60,000 characters server-side.
  - Per-IP in-memory rate limiting on every route that calls a metered IBM
    API (5-10 requests per 5 minutes depending on route cost).
  - Secrets files (.env.local, MCP config) added to .gitignore.

Known irreversible side effects triggered by the app (each gated behind an
  explicit human approval step in the UI, not an automated trigger):
  - Sends real emails (task assignment + delivery package)
  - Posts real messages to a Slack channel and DMs individual users
  - Creates real Jira Epics and Stories in a live Jira Cloud project

Please generate controls covering: moving from single-passcode to full
session/user-account management, secrets-manager migration (currently
plaintext env vars), further input validation for LLM-facing free-text
fields, authorization/RBAC for the 4 modeled roles (currently unenforced
once past the shared gate), and encryption-at-rest for the local state file.
