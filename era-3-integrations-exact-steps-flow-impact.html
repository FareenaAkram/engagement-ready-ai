Integration 1 — Outlook via Office 365 SMTP 10 minutes

Your app currently sends from Gmail (smtp.gmail.com, user fareenaakram18@gmail.com). Switching to Office 365 makes every task email land in Outlook with Fareena.Akram@ibm.com as the true sender — no more "sent from Gmail" header. This is a pure config change. Zero code changes needed.

IBM email restriction: IBM enforces MFA and modern auth on ibm.com mailboxes. Before trying this, check with your IT admin whether SMTP AUTH is allowed on your account. If not, use Option B (App Password) or stay on Gmail for the challenge.

Option A — IBM/Office 365 SMTP direct (requires SMTP Auth enabled)

Open .env.local and change these 4 lines:

- EMAIL_SMTP_HOST=smtp.gmail.com
- EMAIL_SMTP_PORT=587
- EMAIL_USER=fareenaakram18@gmail.com
- EMAIL_PASS=eoyn ivdq hrds ujwp
+ EMAIL_SMTP_HOST=smtp.office365.com
+ EMAIL_SMTP_PORT=587
+ EMAIL_USER=Fareena.Akram@ibm.com
+ EMAIL_PASS=your-ibm-password-or-app-password
+ EMAIL_FROM=Engagement Ready AI <Fareena.Akram@ibm.com>

That's it. Restart with npm run dev. All existing email code in services/task-email-service.ts and services/notification-service.ts uses the appEnv.emailSmtpHost variable — nothing else changes.

Option B — Microsoft App Password (safer for IBM accounts)

  1. Go to myaccount.microsoft.com/security-info
  2. Add sign-in method → App password → give it a name like "ERA Local Dev"
  3. Copy the 16-character password it shows you (only shown once)
  4. Use that as EMAIL_PASS above — your main IBM password does not work with SMTP
Flow impact — what changes in the app
  • All task assignment emails (sent at HITL accept) arrive from Fareena.Akram@ibm.com instead of Gmail
  • The delivery package emails (Executive Summary, Client Email) after final approval arrive from your IBM address
  • Recipients see a legitimate IBM sender — no spam filter risk
  • No UI change. No code change. Just restart the dev server after editing .env.local

Integration 2 — GitHub MCP → Auto-create Issues from Action Plan 2 days

Right now, when the consultant clicks "Accept AI Plan", the app creates Jira tickets (if Jira credentials are set) and sends task emails. GitHub Issues would be a parallel channel — better for teams who track everything in GitHub rather than Jira.

What you need first — your side

1
Create a GitHub Personal Access Token (PAT)
Go to github.com → Settings → Developer settings → Personal access tokens → Fine-grained tokens
Permissions needed: Issues: Read & write, Contents: Read (just for the repo)
Set expiry to 90 days. Copy the token — it starts with github_pat_
2
Create a GitHub repository for the engagement
Could be private. Example: ibm-consulting/engagement-era-2025
Note the owner/repo string — you'll use it below
3
Add to .env.local
GITHUB_TOKEN=github_pat_xxxx...
GITHUB_REPO=your-org/engagement-era-2025
4
Add env vars to lib/env.ts
Add to the Zod schema (same pattern as Jira): GITHUB_TOKEN, GITHUB_REPO
Add hasGitHubConfig() guard that returns Boolean(githubToken && githubRepo)
5
Create services/github-service.ts
Single function: createGitHubIssue(title, body, labels, assignee)
Calls POST https://api.github.com/repos/{owner}/{repo}/issues
Headers: Authorization: Bearer {GITHUB_TOKEN}, Accept: application/vnd.github+json
6
Call it from app/api/hitl-decision/route.ts
After setTaskAssignments(assignments), loop through each assignment and call createGitHubIssue()
Issue body = task instructions. Labels = priority (critical, high) + role (architect)
Store the returned issue URL in the task assignment record
7
Webhook: GitHub Issue closed → mark task done (optional but powerful)
In your GitHub repo: Settings → Webhooks → Add webhook
Payload URL: https://your-ngrok-url/api/github/webhook
Content type: application/json
Events: Issues only
Create app/api/github/webhook/route.ts that reads action === 'closed' and calls /api/task/update

The actual GitHub API call — what the service looks like

// POST https://api.github.com/repos/{owner}/{repo}/issues
{
  "title": "[ERA] Fix authentication requirements — Security Lead missing",
  "body": "**Role:** Architect\n**Priority:** Critical\n**Due:** Week 1\n\n**Instructions:**\nSchedule a security architecture session...\n\n---\n_Created by Engagement Ready AI after readiness assessment_",
  "labels": ["critical", "architect", "era-remediation"],
  "assignees": []   // GitHub username if you have it
}
Flow impact — what changes in the app
  • After HITL accept: alongside Jira tickets and emails, GitHub Issues are created — one per action plan item
  • Action Center: each task card gains a "GitHub Issue" link badge (you'd add this to the UI)
  • When engineer closes the GitHub Issue: webhook fires → POST /api/task/update → Action Center updates automatically, no app visit required
  • All-done detection still works as-is — /api/task/update already checks if all tasks complete and advances to ready-for-review
  • Existing flow is unaffected — GitHub is additive alongside Jira, not a replacement
Bob GitHub MCP note: Bob's GitHub MCP server is for Bob to read/write your code repo during development. It is NOT the right tool for this integration. The production GitHub Issues creation is a direct REST API call from your Next.js service — it doesn't go through Bob at all. Use Bob's MCP during development to help you write and test the github-service.ts code.

Integration 3 — MS Graph Calendar → Auto-book Missing Workshops 3 days

This is the most impressive integration for a demo. watsonx already identifies missingWorkshops with a title and reason (e.g. "Security & Compliance Workshop", "Data Migration Workshop"). MS Graph lets you turn that list directly into Outlook calendar invites — the AI finds the gap AND schedules the fix.

What "missing workshops" look like in your data right now

// From AIAnalysisResult.missingWorkshops (already produced by Granite):
[
  {
    title: "Security & Compliance Workshop",
    reason: "Define authentication approach, security architecture, and GDPR obligations",
    priority: "critical"
  },
  {
    title: "Data Migration Workshop",
    reason: "Inventory legacy AS/400 schema, estimate data volume, define migration strategy",
    priority: "critical"
  },
  {
    title: "Architecture Decision Workshop",
    reason: "Confirm cloud provider, integration patterns, and technical approach",
    priority: "high"
  }
]

This data is already in your state file after every assessment. You just need the calendar booking step.

Step 1 — Register a Microsoft Entra (Azure AD) app

1
Go to portal.azure.com → Microsoft Entra ID → App registrations → New registration
Name: "ERA Calendar Agent". Account type: Accounts in this org only. No redirect URI needed (server-side).
2
Add API permissions
API permissions → Add → Microsoft Graph → Application permissions (NOT delegated):
Calendars.ReadWrite — to create calendar events
Mail.Send — to send the invite email (optional if you just create the event)
Click Grant admin consent (requires your IT admin for ibm.com tenant)
3
Create a client secret
Certificates & secrets → New client secret → 12 months → copy the Value (not the ID)
4
Copy 3 values from the app overview page
Application (client) ID, Directory (tenant) ID, and the client secret you just created
5
Add to .env.local
MS_TENANT_ID=your-directory-tenant-id
MS_CLIENT_ID=your-application-client-id
MS_CLIENT_SECRET=your-client-secret-value
MS_CALENDAR_SENDER=Fareena.Akram@ibm.com

Step 2 — How the Graph token works (server-side, no user login)

# 1. Get an access token (client credentials flow — no user needed)
POST https://login.microsoftonline.com/{MS_TENANT_ID}/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id={MS_CLIENT_ID}
&client_secret={MS_CLIENT_SECRET}
&scope=https://graph.microsoft.com/.default

# Response: { access_token: "eyJ0..." }

# 2. Create a calendar event on behalf of MS_CALENDAR_SENDER
POST https://graph.microsoft.com/v1.0/users/{MS_CALENDAR_SENDER}/events
Authorization: Bearer {access_token}
Content-Type: application/json

Step 4 — Where in your app to trigger this

The trigger point is in app/api/hitl-decision/route.ts, right after setTaskAssignments(assignments). You have access to review.missingWorkshops at that point. Create a new services/calendar-service.ts with a bookWorkshopInvites(workshops, organiser) function, then call it fire-and-forget (same pattern as the Slack call — don't await it, don't block the response).

// In app/api/hitl-decision/route.ts — add after setTaskAssignments():

if (hasMSGraphConfig() && review.missingWorkshops.length > 0) {
  bookWorkshopInvites(
    review.missingWorkshops,
    stakeholders.consultant.email,
    stakeholders.client.email,
  ).then((r) => console.log(`[hitl-decision] Calendar: ${r.created} invites booked`))
   .catch((e) => console.warn('[hitl-decision] Calendar booking failed:', e));
}

Step 5 — Add the env guard to lib/env.ts

// Add to Zod schema:
MS_TENANT_ID: z.string().optional(),
MS_CLIENT_ID: z.string().optional(),
MS_CLIENT_SECRET: z.string().optional(),
MS_CALENDAR_SENDER: z.string().optional(),

// Add guard function:
export function hasMSGraphConfig() {
  return Boolean(
    appEnv.msTenantId &&
    appEnv.msClientId &&
    appEnv.msClientSecret
  );
}
Flow impact — what changes in the app
  • No change to the HITL flow itself — calendar booking fires after the accept response is already sent (fire-and-forget, like Slack)
  • After "Accept AI Plan": for each workshop in missingWorkshops, a calendar invite is created in the lead consultant's Outlook, with the client contact as an attendee
  • Demo effect: watsonx says "Security Workshop is missing" → consultant clicks Accept → 30 seconds later, calendar invite lands in Outlook. The AI found the gap AND booked the fix
  • Workshop count can be shown in the AI Findings panel — you already have the missingWorkshops array rendered there; you'd just add a "Booking workshops…" indicator
  • Token is cached module-scope (same pattern as your watsonx + ICA IAM tokens) — no per-request token fetches
IBM tenant admin consent required: Application-level Calendars.ReadWrite permission needs an admin to click "Grant admin consent" in the Azure portal. If you can't get that for the IBM tenant, use delegated permissions instead — this requires the user to sign in once via OAuth, but then the app can act on their behalf without needing admin consent. For a challenge demo, the delegated flow is easier to set up quickly.
