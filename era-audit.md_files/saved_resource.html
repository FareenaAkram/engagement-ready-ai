Engagement Ready AI — Project Audit

Reviewed 2026-07-12 · Next.js 15 app for IBM Consulting engagement readiness, built on watsonx.ai + ICA + Context Studio

TL;DR

The safe path works: draft → AI assessment → HITL decision → task tracking → final approval → delivery all run end-to-end without crashing, because every IBM/ICA integration has a mock fallback and the app is built to degrade gracefully when credentials are missing. That's genuinely well done.

The live path is unproven: real ICA/Jira/Slack credentials are either absent or were never confirmed against the real backend. The project's own docs admit this (see "ICA Reality" doc below) — the ICA connection strategy changed at least twice during development and the final approach (Agent-API / Langflow) was still being reverse-engineered by trial-and-error scripts sitting in .bob/.

There are 2 real functional bugs in the core workflow (one can crash a screen, one causes a stale/confusing UI for up to 30s), a handful of dead code / orphaned files, a non-functional Settings page, and one important security issue: live, long-lived bearer tokens are sitting in plaintext in .bob/mcp.json and .env.local.

1. Does the whole workflow actually run?

Stage Trigger Works?
draft → assessment-complete Submit intake → POST /api/readiness-review Works, but see Bug #1
assessment-complete → action-plan-accepted Accept AI plan → POST /api/hitl-decision Works
→ tasks-in-progress First task update → POST /api/task/update Works
→ ready-for-review Last task done → POST /api/task/update Works server-side, client UI goes stale (Bug #2)
→ ready-for-engagement → delivery-package-sent Final approval → POST /api/final-approval → generate-deliverables Works

Every page's fetch() call resolves to a real route — no broken wiring on the happy path. But three things are dead code that looks alive:

  • components/ui/maintenance-tasks.tsx — a fully-built 448-line alternate Action Center that nothing renders. /maintenance-tasks actually renders ica-action-center.tsx. If anyone edits this file expecting it to change the app, nothing happens.
  • app/api/ica-agent/assign-tasks/route.ts and app/api/advance-stage/route.ts — fully implemented, zero callers anywhere in the app.
  • app/api/debug-watsonx/ — empty folder, no route.ts, would 404.

Bug #1 — a shape-deviant Granite response can crash the readiness-review screen

services/dashboard-service.ts (submitReadinessReview) builds the AI result and returns it straight to the browser without running it through normaliseReview() — the one normalization function AGENTS.md calls "mandatory." Combined with the fact that tryParseJson() in watsonx-service.ts does zero schema validation (a syntactically-valid but wrong-shaped Granite reply is accepted as status: 'success'), components/ui/readiness-review.tsx:708 does result.criticalIssues.length with no guard. If Granite ever omits or mistypes that field, this throws on the very next render after the consultant clicks "Run AI assessment." Low probability, high visibility.

Fix: pipe the result through normaliseReview() before returning it (one-line change), and/or add a minimal zod shape check on the parsed Granite JSON.

Bug #2 — Action Center shows the wrong panel for up to 30s after the last task is completed

Marking the last task done invalidates only the ['task-list'] query, not ['dashboard']/['ai-analysis']. Since those have a 30s staleTime and no polling, the client's workflowStage doesn't refresh — so ICAActionCenter falls through to the generic "keep working on tasks" panel instead of showing Approve for Engagement, even though the server has already advanced the stage. The consultant has to wait or manually reload.

Fix: in the task "mark done" mutation's onSuccess, also invalidate ['dashboard'] (one line).

Minor issues found

  • app/api/settings/route.ts is the only GET route missing export const dynamic = 'force-dynamic'.
  • app/api/notify/route.ts mislabels which channel failed when the requested channel list excludes one of ica/slack/email (index-based mismatch).
  • data/mock-dashboard.ts's analytics field is never overlaid with live data (harmless today — nothing reads it — but a trap for future code).
  • workflowStage never literally equals 'tasks-complete' even though it's a defined stage (only appears in history labels) — fine today, but a landmine for future === 'tasks-complete' checks.
  • readWorkflowState/writeWorkflowState swallow filesystem errors with no logging at all — a corrupted state file would silently reset the whole engagement with zero trace.

The Settings page doesn't actually do anything

components/ui/settings.tsx has no POST /api/settings to save to — edits vanish on refresh. Worse, the "current settings" panel always shows the server's hardcoded defaults, not your edits (data?.data ?? settings — the query always wins). None of its 4 fields (engagement label, consultant name, auto-refresh interval, animation toggle) are read anywhere else in the app. It's pure decoration right now.

2. ICA task assignment & "Generate Delivery Assets" — deep dive

There are genuinely two separate ICA features wired into two different screens; worth knowing so you don't conflate them.

A) Task assignment (QA Review → Accept AI Plan)

Accept plan -> POST /api/hitl-decision
  -> writes engagement package to .next/tmp/ica-packages/*.json (always succeeds)
  -> pushToICAAgenticApp() - raw JSON-RPC "tools/call" to the ICA MCP gateway
  -> assignTasksViaICA() - tries Langflow HTTP call -> then ICA Agent-API (A2A) call -> then mock
  -> if ICA returns 0 emails, falls back to local nodemailer send

Verdict: the code is real (real HTTP calls, real auth headers) but the Jira-ticket-creation and Slack-posting for this step are not done by this app's code — they're a natural-language instruction embedded in the prompt sent to the external ICA agent ("...create Jira tickets, post to Slack..."), and the app just trusts whatever JSON comes back. In mock mode (no ICA agent reachable), it fabricates ERA-100, ERA-101 ticket numbers and explicitly marks accepted: false — that part is honest, not disguised as real.

A real bug here: hasICAAgenticConfig() checks ICA_A2A_KEY, but the code it gates authenticates using a different variable, ICA_BEARER (and the error message even says 'ICA_BEARER not set' while checking the wrong key). In your current .env.local both happen to be populated so it's masked — but it's a latent bug that would misfire in a leaner config, and it also feeds the "live/mock" status badge in the UI, so that indicator can't be fully trusted.

Also confirmed: the .bob/test-ica-*.mjs scripts are active reverse-engineering of the ICA Agentic App's session/tool protocol by trial and error — brute-forcing endpoint names, testing multiple payload shapes. That's a strong signal the "real" MCP push (ingest_engagement_package) has not been confirmed working against the live ICA backend — it's a best-guess contract, not a verified one.

B) Generate Delivery Assets (QA Review "ICA Accelerator" buttons + Final Approval)

Two different generators share the name:

  1. On-demand single asset (executive summary, RAID log, user stories, etc. — 18 types) — one Granite call per click. Works correctly, has an honest "(Demo Mode)" fallback label when watsonx isn't configured. But results live only in component useState — refresh the page and everything generated is gone. Nothing is persisted or sent anywhere.
  2. Final-approval delivery package (executive summary, client email, internal email, Jira epic, Slack message) — this one is persisted to the workflow state file, and does trigger real side effects: real nodemailer send, real Slack webhook post, real Jira Epic+Story creation via a genuine Jira Cloud REST client — all gated correctly, all silently no-op today because JIRA_* and SLACK_WEBHOOK_URL aren't set in your .env.local.

Suggested improvements for this flow:

  • Persist on-demand generated assets (flow A) into the workflow state file the same way flow B does, so they survive a refresh and show up in the delivery package.
  • Fix the ICA_A2A_KEY/ICA_BEARER mismatch so the "live" badge is trustworthy.
  • Delete the two dead/duplicate routes (ica-agent/assign-tasks, advance-stage) or wire them in — right now they're confusing maintenance surface with no purpose.
  • Add a lightweight retry/confirmation step after the ICA agent call: since Jira/Slack creation for Phase 1 is only a claim from the external agent's text response, consider having the app independently verify (e.g., a follow-up read call) rather than trusting self-reported JSON.

3. Security note (please action this)

.bob/mcp.json and .env.local contain live, long-lived bearer tokens in plaintext (one ICA gateway token has no expiry until 2096). This folder isn't a git repo yet, which limits accidental push risk today, but:

  • If you ever git init this project, make sure .env.local and .bob/mcp.json are in .gitignore before the first commit.
  • Treat these as compromised if this folder is ever shared/zipped/uploaded anywhere — rotate them.

4. Integrating Jira & Slack through ICA — simple path (not the complex one)

Your docs describe three different ICA connection strategies built at different times (direct REST → MCP-via-Orchestrate → Agent-API/Langflow A2A). That churn is likely your biggest productivity drag — pick one and stop re-litigating it. Given what's already built and working in your codebase, here's the lowest-complexity path:

Recommended: keep ICA out of the Jira/Slack critical path. Let this app talk to Jira and Slack directly, and use ICA only for the parts only ICA can do (task assignment routing, org-aware notifications).

Why: services/jira-service.ts and services/notification-service.ts's Slack webhook are already real, already tested-shape, already working the moment you provide credentials — no protocol reverse-engineering needed, unlike the ICA Agentic App MCP path. Concretely:

  1. Slack — 10 minute setup. Create a Slack app → enable Incoming Webhooks → pick a channel → copy the webhook URL → set SLACK_WEBHOOK_URL in .env.local. Nothing else to change; hasSlackConfig() flips on and the delivery flow starts posting for real.
  2. Jira — 15 minute setup. Create an API token in your Atlassian account → set JIRA_BASE_URL, JIRA_EMAIL, JIRA_API_TOKEN, JIRA_PROJECT_KEY → hasJiraConfig() flips on and Epic+Story creation starts firing for real on final approval.
  3. Where ICA still adds value: keep using the ICA Agent-API call for assigning tasks to the right consulting-team roles (that routing logic genuinely benefits from ICA's org knowledge) — but stop asking the ICA agent to "also create the Jira ticket and post to Slack" in the same prompt. Split responsibility: ICA decides who/what; this app's own Jira/Slack clients execute the write. That removes your two least-reliable dependencies (unverified MCP protocol, trusting an LLM's self-reported "I created the ticket") from the two actions you most need to be correct (Jira tickets, Slack pings).
  4. Once that's stable, if you still want the "official" ICA-mediated route for compliance/governance reasons, layer it back in behind the same hasXConfig() guard pattern you already use — additive, not a rewrite.

This is deliberately the "boring" option — it uses code you already have working, skips a protocol that's still being reverse-engineered, and gets you a demoable, correct Jira+Slack flow in under an hour instead of more MCP archaeology.

5. Productivity / workflow improvement suggestions (roughly ordered by effort:impact)

Quick wins (under an hour each):

  • Fix Bug #2 (add invalidateQueries(['dashboard']) to the task-complete mutation) — removes the most user-visible glitch.
  • Add normaliseReview() to submitReadinessReview()'s return path — closes the one crash risk.
  • Add export const dynamic = 'force-dynamic' to app/api/settings/route.ts.
  • Delete or clearly comment out the 3 dead files (maintenance-tasks.tsx, ica-agent/assign-tasks/route.ts, advance-stage/route.ts) so future edits don't target them by mistake.
  • Fix the ICA_A2A_KEY vs ICA_BEARER mismatch in hasICAAgenticConfig()/getICAStatus().

Medium (a session each):

  • Persist on-demand-generated ICA assets (the QA Review accelerator panel) into workflow state so they survive refresh, instead of living only in useState.
  • Wire Jira + Slack directly (per §4) — biggest real productivity unlock, since it turns "demo mode" into an actually-working delivery pipeline today.
  • Make the Settings page functional: add a POST /api/settings, persist to the workflow-state file (or a small config file), and fix the data?.data ?? settings precedence bug so user edits actually display.

Bigger (worth a deliberate decision, not urgent):

  • Pick ONE ICA connection strategy (direct REST vs MCP vs Agent-API/Langflow) and delete the others' code paths — right now three strategies coexist, which is exactly the kind of complexity to avoid. Recommend: Agent-API/Langflow for task routing (already working in mock mode, closest to "done"), direct Jira/Slack clients for delivery (per §4), and drop the raw MCP pushToICAAgenticApp push entirely unless the real contract gets confirmed by IBM.
  • Add basic logging (console.warn) to the two silent catch-alls in lib/workflow-state.ts so a corrupted state file doesn't fail invisibly.

Bottom line

Nothing is fundamentally broken — the app runs, degrades gracefully, and the "demo mode" story is honest and consistent. The two real bugs are small, fixable in under an hour combined. The biggest lever for "everything actually working" isn't more code — it's committing to one ICA integration strategy and turning on the Jira/Slack credentials directly rather than routing them through an unverified ICA protocol.
