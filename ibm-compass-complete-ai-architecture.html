01 System Overview — The Three-Layer Architecture

IBM Compass is designed as a three-layer AI system: an Orchestration Layer driven by watsonx Orchestrate, a Cognitive Layer of specialised sub-agents powered by IBM Granite LLMs, and a Grounding Layer providing RAG, memory, and tool access. These layers sit behind a unified API gateway and interact with the IBM enterprise tool ecosystem.

Key Design Principle: Every agent is stateless and idempotent. All state is held in the Grounding Layer. This allows horizontal scaling, replay of actions, and full audit trails — mandatory for enterprise governance.

03 Orchestrator Agent — Delegation Design

The Compass Orchestrator is the single point of entry for all requests. It runs on Granite 34B Instruct with a system prompt that encodes the full capability map of all sub-agents, the delegation policy, and the guardrail rules. It does not execute tasks itself — it reasons, plans, and delegates.

Recommendation: Yes — the Orchestrator should always delegate. The Orchestrator should never directly write to Jira, send emails, or query knowledge. Delegation maintains a clean separation of concerns, allows per-agent observability, and makes failure isolation possible. The Orchestrator's only job is to think and route.

Orchestrator execution model: The Orchestrator follows a Plan → Delegate → Observe → Synthesise loop:

  • 1
    Intent Classification — Granite 34B classifies the incoming request into one of 12 intent categories (briefing, knowledge_query, meeting_process, draft_request, risk_check, approval_action, calendar_optimise, compound). Uses watsonx NLP classifier as a pre-filter for speed.
  • 2
    Task Decomposition — For compound requests (e.g., "prepare me for my 3pm client call"), the Orchestrator breaks this into sub-tasks: (a) fetch meeting context, (b) RAG-query relevant account docs, (c) surface recent Jira items, (d) draft pre-brief. Tasks are dependency-ordered.
  • 3
    Parallel Delegation — Independent sub-tasks are dispatched in parallel to multiple agents via watsonx Orchestrate's async skill invocation. Dependent tasks are chained. This is the primary source of response-time optimisation.
  • 4
    Result Aggregation — The Orchestrator receives all agent outputs and synthesises a unified, coherent response. It resolves conflicts (e.g., Knowledge Agent and Risk Agent give different project status) by sourcing priority rules from governance config.
  • 5
    Guardrail Check — Before returning or acting, the Orchestrator runs all outputs through IBM watsonx.governance's content shield: PII check, hallucination risk flag, action-confidence threshold (high-risk actions require explicit user confirmation).

04 Agent Communication Patterns

Compass uses three communication patterns depending on the task type, latency requirement, and whether agents need to coordinate:

Pattern 1

Request/Response (Sync)

Used for user-initiated queries requiring immediate response (<3s). Orchestrator dispatches skills via watsonx Orchestrate REST API. Agents return structured JSON. Used for chat interactions, knowledge queries, and briefing delivery.

Pattern 2

Event-Driven (Async via IBM MQ)

Used for background monitoring and proactive triggers. The Risk Agent and Approval Agent publish to IBM MQ topic queues when anomalies are detected. The Briefing Agent subscribes and incorporates signals into the next briefing cycle.

Pattern 3

Scheduled Batch (cron + Kafka)

Used for the nightly/morning indexing pipeline: re-ingest changed documents, recompute user context vectors, refresh risk scores. Kafka streams connector pipes data from Jira/GitHub/Confluence into the watsonx.data pipeline.

Pattern 4

Agent Handoff (Shared Context)

When an agent needs output from another (e.g., Draft Agent needs Knowledge Agent's RAG output), the Orchestrator passes a context bundle as a JSON payload. No agent calls another directly — all routing passes through the Orchestrator.

All agent-to-agent message envelopes conform to a standard schema including: request_id user_id session_id confidence citations[] action_type requires_confirmation. This ensures full traceability through watsonx.governance.

05 Memory Architecture — Three-Tier Memory Design

Enterprise AI assistants fail without structured memory. Compass implements a three-tier memory model matching the temporal horizon of each memory type to the right storage technology.

Memory Tier Scope Technology TTL Contents
Working Memory
In-session context		 Single conversation / task Redis Cluster 2 hrs Current session messages, intermediate agent outputs, task plan state, tool call history
Episodic Memory
Recent history		 Last 30 days per user PostgreSQL + pgvector 30 days rolling Past meeting summaries, prior action items (done/open), recent document queries, approval states, drafts produced
Semantic Memory
User profile & preferences		 Persistent per user PostgreSQL + pgvector Indefinite Writing tone profile, preferred communication style, project ownership list, org chart position, skill tags, trust-level for auto-actions
Memory Retrieval Strategy: At each agent invocation, the Orchestrator performs a memory retrieval step — a vector similarity search over episodic and semantic memory keyed on the current request embedding. The top-5 memory chunks are injected into the agent's context window as a "memory block", giving the agent rich personal context without blowing context limits.
Privacy enforcement: Memory is strictly user-scoped — enforced at the storage layer via row-level security in PostgreSQL. No user's memory is accessible to any other user's agent call, even within the same team. Sensitive fields (salary, performance ratings) are excluded from memory entirely via a field-level suppression list in the data pipeline.
06 RAG Architecture — Retrieval-Augmented Generation

The Knowledge Agent is entirely RAG-driven. It never answers factual questions from model weights alone — all answers must be grounded in retrieved enterprise documents. This is the primary defence against hallucination in enterprise context.

RAG ComponentTechnologyRationale
Embedding model ibm/slate-125m-english-rtrvr IBM-native, on-premises deployable, no data egress. Trained on enterprise language patterns.
Vector store Elasticsearch 8.x (HNSW dense vectors) Already in IBM's enterprise stack. Supports hybrid BM25+dense in a single query.
Query rewriting Granite 8B Instruct Lightweight rewriter expands IBM abbreviations (e.g., "GTS", "ELM", "SOW") to improve recall.
Reranker IBM cross-encoder (watsonx.ai) Precision-focused reranking reduces irrelevant chunk injection — critical for enterprise accuracy.
Chunk strategy Semantic chunking (512 tokens, 64 overlap) Preserves sentence coherence across document boundaries. Better than fixed-size chunking for policy docs.
Citation enforcement Structured output + post-processor Generated answer must include document_id, chunk_id, and page reference for every factual claim.
Contextual RAG (advanced): For each chunk at index time, Compass generates a "context header" using Granite 8B that describes where in the document the chunk appears and what broader topic it belongs to. This context header is prepended to the chunk embedding, dramatically improving retrieval precision for policy and procedural documents.
07 Enterprise Data Indexing Strategy

Data indexing is the foundation of Compass's knowledge quality. The architecture supports four indexing modes to handle the variety of enterprise data freshness requirements.

ModeTriggerSourcesLatency Target
Real-time (streaming) Webhook / Kafka event Jira ticket updates, Slack messages (flagged), GitHub commits < 30 seconds
Near-real-time (micro-batch) Every 15 minutes Calendar changes, email summaries, ServiceNow approval changes < 20 minutes
Nightly batch 02:00 user local time Confluence pages, Box files, SharePoint docs, GitHub READMEs < 8 hours
On-demand (cold path) User query triggers a miss Any document URL the user provides; ad-hoc indexing on cache miss < 10 seconds

The indexing pipeline stages are:

  • 1
    Ingest — IBM DataStage connectors pull from source APIs. Kafka Connect ingests streaming events. All data tagged with: source_system, doc_id, owner_id, access_classification (PUBLIC/INTERNAL/CONFIDENTIAL/RESTRICTED), last_modified.
  • 2
    Parse & Clean — Apache Tika for format extraction (PDF, DOCX, PPTX, HTML). IBM Watson NLP pre-processor strips boilerplate, normalises IBM taxonomy terms, detects language.
  • 3
    Chunk — Semantic chunking using sentence boundary detection. Each chunk inherits parent document's access_classification — retrieval is access-controlled at chunk granularity.
  • 4
    Enrich — Granite 8B generates a context header per chunk. Named entity extraction tags IBM product names, project codes, people names. Metadata enriched: team, business_unit, client_id.
  • 5
    Embed — ibm/slate-125m-english-rtrvr generates dense vectors per chunk. Stored alongside BM25 inverted index in Elasticsearch.
  • 6
    Access Control Enforcement — At query time, the retriever filters Elasticsearch to chunks where access_classification ≤ user's clearance AND doc_id ∈ user's permitted_docs (from w3 SSO group membership). Users never see content they don't have access to.

11 Security & AI Governance
Hallucination

RAG-Only Factual Answers

All factual outputs from Knowledge Agent must cite a retrieved chunk. Answers with confidence <0.75 are flagged as "unverified" and shown to user with a disclaimer. Draft Agent uses a context-injection check to ensure claims trace to source data.

PII

IBM Watson NLP PII Shield

All LLM outputs pass through watsonx.governance PII detector before delivery. Salary, personal address, performance data are suppressed at the data layer and never indexed. Cross-user data isolation enforced via row-level security.

Audit

Full Action Audit Trail

Every agent action (Jira write, email send, Confluence update) is logged to IBM Cloud Activity Tracker with: user_id, agent_id, action, input_hash, output_hash, timestamp. Immutable audit log retained 7 years per IBM compliance policy.

Trust

Human-in-Loop for High-Risk Actions

Actions scored as high-risk (send email to external client, approve procurement >$10k, close Jira epic) require explicit user confirmation before execution. Trust level per action category is configurable per user and team policy.

watsonx.governance integration: All Compass LLM calls are registered in watsonx.governance with model ID, prompt hash, and response metadata. This provides IBM with a full AI model usage registry, drift detection, and regulatory compliance evidence — essential for enterprise deployment and EU AI Act readiness.
12 Enterprise Scale Design — 100,000 Users

Compass is designed to serve 100,000 concurrent IBM employees at Phase 4, scaling to 280,000 and beyond. The architecture is horizontally scalable at every layer.

ComponentScale StrategyTarget Capacity
Orchestrator Agent Stateless pods on OpenShift; auto-scale via HPA (CPU+RPS). Each pod handles ~50 concurrent requests. 2,000 concurrent orchestrations
Sub-Agent Services IBM Cloud Code Engine serverless functions per agent. Zero-scale when idle, burst to 500 instances. 10,000 agent calls/minute
LLM Inference (Granite) watsonx.ai dedicated GPU nodes (A100/H100). Granite 13B on 8-way tensor parallel. Request queuing with priority lanes (briefing > background). 500 LLM requests/second
RAG Elasticsearch 10-node Elasticsearch cluster, 3 replicas per index shard. Index partitioned by business_unit for locality. Read replicas for query load. 50M document chunks, 5,000 QPS
Redis Working Memory Redis Cluster (6 nodes). Session keys partitioned by user_id hash. 2-hour TTL auto-expiry. 100,000 concurrent sessions
Kafka Event Bus IBM Event Streams (managed Kafka). 24 partitions per topic. Retention 7 days. Consumer groups per agent type. 100,000 events/second peak
PostgreSQL Memory Store IBM Cloud Databases for PostgreSQL. Primary + 2 read replicas. pgvector index (HNSW) on episodic memory. Partitioned by user cohort. 100M episodic memory records
Daily Briefing Delivery Staggered cron: briefings generated in rolling 3-hour window (04:00–07:00 UTC across all timezones). Pre-generated and cached in Redis keyed by user_id. 100,000 briefings in <3 hours
Latency targets: Interactive queries (chat) <3 seconds P95. Daily briefing delivery (pre-generated) <200ms. Background risk detection (async) best-effort <15 minutes lag. Meeting processing (webhook triggered) <90 seconds end-to-end.
Year 2 — Commercialisation: When IBM Compass is productised as IBM watsonx Compass, the architecture supports multi-tenancy via namespace isolation in OpenShift, per-tenant Elasticsearch index partitions, per-tenant Granite model fine-tuning, and per-tenant API keys — enabling Fortune 500 customers to deploy their own isolated instance on IBM Cloud or on-premises via IBM Cloud Pak for Data.
